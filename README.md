# fiduflow

A strongly typed Rust DSL for business process applications, under design. This workspace
holds the second spike: a payment flow written in the *machine form* the DSL will generate,
persisted at every wait through user-modelled tables, translated to Lean 4 with Aeneas, and
proved against.

The flow being implemented, its required properties and the persistence contract are
specified in [`PSP_FLOW.md`](PSP_FLOW.md); its last section maps every requirement to the
code, test or theorem that discharges it. [`FILES.md`](FILES.md) explains every file.

Design decisions so far: entities are enums of states with a typestate wrapper; flows are
authored in an async style and lowered to a first-order state machine; each interaction is
co-defined with its response type; the runtime saves the flow's bookmark (which carries the
entity) before every wait and loads it on every response; proofs are about the generated
code that actually runs.

## The UPI PSP pay flow: machine form, persisted and proved

`psp-flow`, the two `*-framework` crates, `psp-app` and `psp-lean` are the second spike of the DSL design (the first, loan onboarding in memory, lives in `~/source/rust-sample`): the pay flow from the
interaction-tree document written in the *defunctionalised* form that a `#[flow]` macro
would generate from an `async`-style body, so that it can be (a) persisted at every wait
and (b) translated to Lean with Aeneas and proved against.

| Piece | What it is |
|---|---|
| `psp-flow` | `no_std`, depends only on the (also `no_std`) framework traits, no closures/`dyn`/strings. `entity.rs` is the `UpiTxn` typestate entity; `events.rs` the interactions, each co-defined with its response via `impl Event { type Response }`; `machine.rs` one typed wait point per `Vis` node with `event`/`resume`, wrapped in `PayerPay`, plus the boundary `event`/`deliver`. |
| `store-framework` | Domain-agnostic, databases only: the `Backend` trait (transactions plus the framework's instance and journal tables, one impl per database; SQLite included). |
| `driver-framework` | Domain-agnostic, flows, `no_std`: the `Event`, `WaitPoint` and `Flow` traits, `Next`, `Stored`; the `Persist<B>` trait the application implements on its flow type to model its own tables; and `Driver<F, B>`. `start` stores the bookmark before the first wait; `deliver` loads it from the database, steps it, stores it again and journals, in one transaction; `pending` rebuilds waiting instances after a crash. |
| `psp-app` | The only domain crate besides `psp-flow`: binds the machine to the framework (`impl Flow`), models the tables in `persistence.rs` (`impl Persist<Sqlite> for PayFlow`: `upi_txn` for the entity, `pay_flow` for the position), plus the demo and the persistence tests. |
| `psp-lean` | `PspFlow/` is generated by Charon + Aeneas from `psp-flow` (never edit). `PspProofs/Pay.lean` proves P1..P5 from the document against the generated `step`. |
| `scripts/translate-psp.sh` | Regenerates `PspFlow/` and builds the proofs, using the pinned binaries in `~/source/aeneas-namma-cloud/.tools` (override with `AENEAS_TOOLS`). |

Run:

```sh
cargo test -p psp-app                # persistence contract, crash recovery, round trips
cargo run -p psp-app --bin demo      # prints upi_txn.state after every interaction
scripts/translate-psp.sh             # Rust -> LLBC -> Lean, then `lake build` incl. proofs
```

What the proofs say (`psp-lean/PspProofs/Pay.lean`), all about the generated code:

| Property | Statement | Proof |
|---|---|---|
| P1 user always notified | every run ends with a `Notify`/`ShowError` event | case bash on `step` + induction on runs |
| P2 MPIN at most once | `CollectMpin` appears at most once in any run from `start` | budget invariant per state |
| P3 all responses handled | each wait point's `resume` takes exactly its event's response type | a typing fact, no theorem needed; `deliver_sound` shows the boundary only ever calls `resume` |
| P4 terminates | a run from `s` has at most `measure s + 1` interactions | ranking function decreases on every `Wait` |
| P5 NPCI needs auth | `ReqPay` is only issued from `AtReqPay`, which holds a `Txn Authenticated` | by the constructor type |
| P6a id preserved | the terminal entity has the id the flow started with | no transition touches `id` |
| P6b amount validated | every amount reaching a terminal state is non-zero and within the cap | data invariant carried through every `Wait` |

Deliberately out of spike 2, to be added as a separate effort: typed authorisation on
transitions (`Authorized<Role>` parameters and `ensure` clauses, as in spike 1's `loan.rs`).
The pay flow currently treats every transition as performed by the system, with the user's
authority implicit in the responses.

Two things the spike settled:

* Variant B (`async fn`) cannot be translated by Charon today (issue #609), and variant A's
  `Box<dyn FnOnce>` needs `dyn Trait` which is also unsupported. The machine form is what
  must be generated for proofs, and it is also what the runtime executes, so there is only
  one artefact.
* Aeneas needs the Rust module containing the entity not to share a name with a common
  local variable (`txn`), otherwise the generated Lean parses `txn.TxnX.method` as a field
  projection. Hence `entity.rs`.
