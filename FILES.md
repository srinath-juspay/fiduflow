# File guide

A file-by-file explanation of this workspace, in dependency order. Every file is either
what a DSL macro would generate, what an application would write against the DSL, or what
the runtime provides; the DSL itself does not exist yet.

The first spike (loan onboarding, in-memory, `bp-core` + `loan-*`) lives in
`~/source/rust-sample`; this workspace is the second.

---

## Workspace root

### `Cargo.toml`
The workspace manifest: the four Rust crates, with `rusqlite` pinned for everyone.

### `PSP_FLOW.md`
The requirements: the parties, the entity lifecycle, the interactions with their response
types, the subflows and the inlined tree in the interaction-tree notation, the seven paths,
the properties P1 to P6 as requirements, the persistence contract, what is deferred, and a
table mapping each requirement to the file, test or theorem that discharges it. Read this
before the code.

### `README.md`, `FILES.md`
Orientation and this guide.

### `scripts/translate-psp.sh`
Regenerates the Lean model from `psp-flow` and builds the proofs. Runs Charon on the crate
to produce `build/psp_flow.llbc`, runs Aeneas on that to produce `psp-lean/PspFlow/*.lean`,
then `lake build`. It uses the pinned binaries in `~/source/aeneas-namma-cloud/.tools`;
override with `AENEAS_TOOLS`, `CHARON` or `AENEAS`.

### `build/psp_flow.llbc`
Charon's intermediate output for `psp-flow`: the crate's MIR lowered to LLBC, the input
Aeneas consumes. Binary, regenerated by the script, safe to delete.

## `psp-flow`: the pure machine

The UPI PSP "Pay" flow from the interaction-tree document, in the *defunctionalised* form a
`#[flow]` macro would generate from an async-style body. Hand-written here so it can be fed
to Charon and Aeneas unchanged: `no_std`, no dependencies, no closures, no `dyn`, no
strings, no `async`, and `Debug`/`PartialEq` derives only behind the `runtime` feature so
the translated surface stays small.

### `psp-flow/Cargo.toml`
No dependencies. The `runtime` feature enables the derives the runtime and tests need;
Charon runs with it off.

### `psp-flow/src/lib.rs`
Module wiring and re-exports.

### `psp-flow/src/values.rs`
Value types as plain newtypes over integers: `PayerId`, `Vpa`, `Amount` in paise, `Mpin`,
`Ref`, `TxnId`. `Reason` and `Status` are enums so no string ever appears. `RawIntent` is
what the user typed, `ValidIntent` what survived validation, `PayRequest` what goes to
NPCI. `validate_pay_intent` is the one pure decision of the flow.

### `psp-flow/src/entity.rs`
The `UpiTxn` entity in the same shape as `loan.rs`: one struct per state (`Initiated`,
`Authenticated`, `Submitted`, `Deemed`, `ReversalPending`, `Success`, `Failed`,
`Reversed`, `Abandoned`), the `Terminal` state-set enum, the `Txn<S>` typestate wrapper
with public fields so the persistence layer can rebuild it, and the transitions as inherent
methods. `build_req_pay` lives on `Txn<Authenticated>`, which is property P5 as a type.
The module is named `entity` rather than `txn` because a module name that matches a
common local variable breaks the generated Lean.

### `psp-flow/src/events.rs`
The interactions, each co-defined with its response: `trait Event { type Response; }` and
one struct per event, so `<AwaitCallback as Event>::Response` is `Callback`. Deadlines are
part of the event and the expired-deadline cases are variants of the response, so an
exhaustive `match` cannot forget them. `AnyEvent` and `AnyResponse` are the runtime
boundary, where a stored instance must say what it waits on and a response arrives as
data; `AnyEvent::party` and `is_user_notification` live there. There is no `accepts`: the
pairing is in the types.

### `psp-flow/src/machine.rs`
The flow as a machine, and the file the whole second spike is about:

* One struct per `Vis` node of the document's inlined tree (`AtAwaitCallback`,
  `AtNotifySuccess`, ...), carrying the locals live at that point, always the typed entity
  handle and sometimes a little more. Each has `event()`, what it waits on, and
  `resume(r)`, whose parameter type is `<ItsEvent as Event>::Response`, so a mismatched
  response is unrepresentable inside the machine. `resume` is the `λ(response) → ...` of
  that node.
* `PayerPay` wraps the wait points so a stored instance is one value; `Next` is
  `Wait(bookmark)` or `Done(terminal entity)`.
* `event(&s)` and `deliver(s, r)` are the runtime boundary: `deliver` decodes an
  `AnyResponse` for the bookmark's event and calls `resume`; it is the only place a
  `Mismatch` can occur. The DSL would generate both.
* `start` builds the entry state.

The runtime saves `PayerPay` before performing `event(&s)`, loads it when the response
arrives, and calls `deliver`. Nothing else ever runs.

## `store-framework`: storage (domain-agnostic)

### `store-framework/Cargo.toml`
No dependencies except `rusqlite` behind the default `sqlite` feature, so a deployment
with another database can turn it off.

### `store-framework/src/lib.rs`
Databases only. `Backend`, implemented once per database, owns transactions (`begin`,
`commit`, and the rule that a dropped transaction rolls back) and the framework's own
tables: the instance registry with its status and response counter, and the journal.
Also `InstanceId`, `Status`, `InstanceInfo`, `JournalEntry` and `JournalRow`, the record
types the trait exchanges. Nothing here knows what a flow is.

### `store-framework/src/sqlite.rs`
`Sqlite`, the first backend. `open` creates the two framework tables; `connection` exposes
the raw connection for application queries. The `Backend` impl is a dozen short SQL
statements. A Postgres backend would be this file again with different SQL.

## `driver-framework`: the flow runtime (domain-agnostic)

### `driver-framework/Cargo.toml`
Depends on `store-framework` with its SQLite feature off; the driver never names a
database.

### `driver-framework/src/machine.rs`
What the runtime needs to know about a flow, and nothing else. `Flow` is the trait a
`#[flow]` macro would implement for a generated machine: a bookmark type `State`, a
terminal value `Done`, the `Event` and `Response` types, and the two pure functions
`event` and `step`; `step` returns `Err(Refused::Mismatch)` when the response does not fit
the wait. `Refused` is owned by the framework so every flow reports the same thing. `Next` is what `step` returns. `Stored` is what the
runtime keeps per instance, a bookmark or the finished value.

### `driver-framework/src/lib.rs`
Two things. `Persist<B>` is the contract an application implements on its flow type, for
example `impl Persist<Sqlite> for PayFlow`: `schema` is the DDL for the application's
tables, `save` turns a `Stored` object into rows, `load` turns rows back. It lives here
rather than in the store crate because it is about flows, and it is implemented on the
flow type rather than the stored object because that is the only local type an
application has, which Rust's orphan rules require.

`Driver<F, B>`, generic over the flow and the backend, is the persistence contract in four
methods. `new` creates the application's tables through `Persist::schema`. `start` stores
the first bookmark and returns the first event. `deliver` opens a transaction, checks the
instance is still waiting, loads the bookmark from the database, computes the next step,
journals, saves the new bookmark, advances the counter and commits; a violation returns
before the commit so the transaction rolls back. `pending` rebuilds every waiting instance
from the tables for crash recovery. `journal` reads the log back. `DriverError` and
`DeliveryOutcome` are the result types.

## `psp-app`: the UPI pay flow on the framework (domain)

### `psp-app/Cargo.toml`
Depends on `psp_flow` with its `runtime` feature, the two framework crates, and
`rusqlite` for the application's own SQL.

### `psp-app/src/lib.rs`
`PayFlow`, the flow as the framework sees it: `impl Flow for PayFlow` names the bookmark,
boundary and terminal types and forwards `event` and `step` to the generated-shaped
functions in `psp_flow`. This is what `#[flow]` would generate. Also the concrete stack:
`PayDriver` is `Driver<PayFlow, Sqlite>`, with `open` and `open_in_memory` helpers, and
re-exports for the demo and tests.

### `psp-app/src/persistence.rs`
The storage mapper, hand-written to show what a `#[persist]` derive would generate:
`impl Persist<Sqlite> for PayFlow`. Two tables chosen by the application, `upi_txn` for
the entity (one row per transaction with a `state` column, queryable by support and
reconciliation) and `pay_flow` for the flow position (which bookmark, plus its extra
locals). `EntityRow`/`FlowRow` are rows about to be written, `EntityDb`/`FlowDb` rows just
read; `rows_waiting` and `rows_finished` map a bookmark to rows; `rebuild` maps rows back,
recomputing the one derived field rather than storing it; `reason_str`/`reason_parse` are
the enum codec; and the SQL upserts and selects. `entity_state` is the query a support
tool would run.

### `psp-app/src/bin/demo.rs`
Drives three scenarios against a file-backed database and prints the `upi_txn.state`
column after every interaction: a happy path; a crash between NPCI's ack and its callback
followed by recovery from the tables alone, through the deemed and forced-reversal paths,
with the journal printed; and a protocol violation that is rejected and rolled back.

### `psp-app/tests/persistence.rs`
Five tests of the contract: the entity state column tracks the lifecycle; crash recovery
resumes from the tables; a violation rolls back and changes nothing; finished and unknown
instances refuse responses; and every one of the fifteen bookmarks and four terminal
states survives a save/load round trip.

## `psp-lean`: the Lean model and proofs

A Lake project. The generated model is never edited; the proofs are hand-written against
it. Packages are reused from `../aeneas-namma-cloud/lean/.lake/packages` through a symlink
so nothing is downloaded.

### `psp-lean/lakefile.lean`
Requires the Aeneas Lean backend at the same commit as the pinned binaries, and declares
two libraries: `PspFlow` (generated) and `PspProofs` (hand-written).

### `psp-lean/lean-toolchain`
Lean 4.31.0, matching the packages being reused.

### `psp-lean/lake-manifest.json`
Copied from the sibling project so Lake resolves the same package revisions.

### `psp-lean/PspFlow.lean`, `psp-lean/PspProofs.lean`
Library entry points; each imports its one module.

### `psp-lean/PspFlow/Types.lean`
Generated by Aeneas. Every Rust type as a Lean inductive or structure, with source
locations in doc comments. `Txn` becomes `structure Txn (S : Type)`, `PayerPay` an inductive
whose constructors carry `Txn Initiated`, `Txn Submitted` and so on, exactly as in Rust.

### `psp-lean/PspFlow/Funs.lean`
Generated by Aeneas. Every Rust function as a Lean definition in Aeneas's `Result` monad
(`ok`, `fail`, `div`), with the Rust `Result<Next, Mismatch>` appearing inside as
`core.result.Result`. The important ones are the per-wait-point `machine.AtX.event` and `machine.AtX.resume`
functions, the boundary `machine.event` and `machine.deliver`, `machine.start`, `events.Event.is_user_notification`,
`events.AnyEvent.is_user_notification` and the entity transitions such as
`entity.TxnAuthenticated.submit`.

### `psp-lean/PspProofs/Pay.lean`
The proofs. Defines `Steps s n` (wait point `s`, resumed with a response of its event's
type, moves to `n`; one constructor per wait point) and `Reaches s evs t` (a complete run
from `s` performing interactions `evs` and ending in terminal entity `t`), then proves,
against the generated `resume` functions, the shape properties and two entity value
properties:

| Theorem | Property |
|---|---|
| `P1_user_notified` | every run contains a user notification; from `done_is_notification`, a run can only finish from a notifying state |
| `P2_from_start` | at most one `CollectMpin` in any run from `start`; from a per-state budget invariant |
| `deliver_sound` | whatever the boundary `deliver` accepts is a typed `Steps`; P3 itself is now a typing fact |
| `P4_terminates` | a run from `s` has at most `measure s + 1` interactions; from `wait_decreases` |
| `P5_reqpay_only_when_authenticated` | `ReqPay` is only issued from `AtReqPay`, which holds a `Txn Authenticated` |
| `P6a_id_preserved` | entity value property: the terminal entity's id is the one the flow started with |
| `P6b_from_start` | entity value property: any amount in a terminal state is non-zero and at most the cap; an invariant `Inv` on the bookmark's entity data, preserved by every step |

A local `case_bash` tactic does every single-step lemma: `cases` on `Steps` gives one case
per wait point with a typed response, then `split` through the generated `if`/`match`
structure, substitute, simplify. There are fifteen cases per lemma, not ninety, because the
mismatch arms no longer exist. All five theorems
depend only on Lean's standard axioms (`propext`, `Classical.choice`, `Quot.sound`).

## How the pieces relate

```
 psp-flow ──── charon ──▶ build/psp_flow.llbc
    ▲                          │ aeneas
    │                          ▼
 psp-app                psp-lean/PspFlow   (generated, never edited)
    ▲                          ▲
 driver-framework       psp-lean/PspProofs (P1, P2, P4, P5, P6a, P6b, deliver_sound)
    ▲
 store-framework                           (no domain words in either framework crate)
```

`psp-flow` is the shape the `#[flow]` macro must generate: it is both what the driver
executes and what Aeneas translates, so there is one artefact and nothing to keep in sync.
